# engine 职责与实现说明

本文面向引擎开发和协作交接，说明 `engine/` 负责什么、当前如何实现、后续应该如何推进。核对日期：2026-09-10。所有路径未特别说明时均相对于 `engine/`。

当前源码已有基础执行器、记录存储和目录恢复实现，不再只是占位骨架；但还没有事务、崩溃恢复和完整并发控制。根目录旧说明中的“待实现边界”不能作为当前功能状态的依据。本文描述实现，不代表所有边界行为均已通过测试。

## 1. 模块边界

| 模块 | 负责的内容 | 引擎如何与它协作 |
| --- | --- | --- |
| `minisql/` | 词法、语法、语义分析、逻辑计划和优化 | 调用已有 `minisql.*` API，接收优化后的 `Plan` 和表结构 |
| `engine/` | 会话编排、计划执行、表达式求值、记录格式、表目录持久化、事务、并发控制、CLI | 本组唯一允许编写功能代码的模块 |
| `页式存储系统/` | 文件读写、固定页分配与回收、缓冲池和脏页写回 | 调用已有 `storage.*` API，将行和目录编码成页字节 |
| `build-modules/` | Maven 构建适配 | 只接入已有源码，不承载功能实现 |

两个已有模块均为受保护的只读模块。记录布局和“表对应哪些页”属于引擎职责；LRU、空闲页链表和文件偏移计算使用存储模块提供的能力。

```text
SQL
  -> EngineSession 调用编译器
  -> 优化后的 Plan
  -> PlanExecutor 执行算子、求值表达式
  -> StorageEngine 记录级接口
  -> PageStorageEngine 编解码记录及目录
  -> BufferPool / PageManager / FileManager
  -> 数据文件
```

## 3. 会话与执行器如何工作

### 3.1 编译和目录衔接

`EngineSession.compile(sql)` 依次调用 `Lexer.tokenize`、`Parser.parse`、`SemanticAnalyzer.analyze`、`Planner.plan` 和 `Optimizer.optimize`，将结果封装到 `CompiledSql`。它使用同一个内存 `Catalog` 完成表名、列名和类型绑定。

CLI 打开存储后先执行 `storage.loadInto(session.catalog())`，让新会话能够编译对已有表的查询。随后一次性编译全部输入语句，编译成功后再按顺序执行各个计划，并非逐条编译后立即执行。

编译器在分析 `CREATE TABLE` 时就会注册内存目录。因此内存中有表不等于该表已经持久化；编译中途失败也可能留下内存目录变化。后续应在引擎内使用临时编译目录和明确的执行成功同步机制，处理失败后的目录一致性。

### 3.2 算子执行方式

| 计划或标记 | 引擎执行步骤 | 返回结果 |
| --- | --- | --- |
| `CreateTablePlan` | 将表名和列定义交给 `storage.createTable` | 空行列表 |
| `InsertPlan` | 将列与值表达式配对，求值，补齐缺省列，构造 `Row`，调用 `storage.insert` | 空行列表 |
| `SeqScanPlan` | 调用 `storage.scan(table)` | 表内记录列表 |
| `FilterPlan` | 先执行 child，再逐行求值 predicate，只保留 `Boolean.TRUE` | 过滤后列表 |
| `ProjectPlan` | 先执行 child，再按计划给出的列顺序构造新行 | 投影后列表 |
| 扫描的 `purpose="DELETE"` | 找到目标表，执行扫描及过滤，将匹配行交给 `storage.delete` | 空行列表；存储返回的删除数目前未向 CLI 展示 |

编译器没有独立 `DeletePlan`，删除通过扫描节点的 `purpose` 标记识别。`SELECT *` 的列展开由编译器完成，引擎读取 `ProjectPlan.columns` 即可。

例如 `SELECT name FROM student WHERE age >= 18;` 对应 `Project -> Filter -> SeqScan`，实际执行先扫描，再过滤，最后投影。当前每层都生成 `List<Row>`，属于全部物化执行，大表会占用较多内存；后续可在引擎内部改为迭代器执行。

### 3.3 表达式与行

`Row` 使用保留插入顺序的只读 Map 保存列值，`get` 按忽略大小写的列名查找。表达式求值递归访问 `Literal`、`ColumnRef`、`UnaryExpr` 和 `BinaryExpr`，支持 `+ - * /`、六种比较、`AND OR NOT` 及负号。`AND`、`OR` 使用短路求值，除零会抛异常。

插入时未指定列的当前默认值为：`INT=0`、`FLOAT=0.0`、`VARCHAR=""`、`BOOL=false`。这是引擎的简化策略，不是 SQL DEFAULT 约束，也不提供 NULL 语义。写入时数值按目标类型转换，写入 INT 使用 `Number.intValue()`，可能截断小数。

后续应补充大小写不同的指定列插入、重复列、数值溢出及整数算术的测试。当前默认值补齐使用区分大小写的 `Map.containsKey`；算术方法中的 Java 三元表达式会进行数值提升，不能仅凭编译器类型检查断言执行值类型始终一致。

## 4. 记录存储如何工作

### 4.1 对外接口

`StorageEngine` 提供 `createTable`、`insert`、`scan`、`delete`、`tables` 和 `close`。执行器依赖这一接口，无需了解页号和字节格式；`PageStorageEngine` 负责具体持久化。

`PageStorageEngine` 构造时打开 `FileManager`，创建 `PageManager` 和使用 LRU 的 `BufferPool`，随后加载元数据。日常数据页读写、分配和回收通过缓冲池进行；当前元数据初始化和加载也直接使用 `PageManager` 的公开 API。

### 4.2 当前文件布局

| 页 | 内容 | 归属 |
| --- | --- | --- |
| 页 0 | 存储模块超块及空闲页管理信息 | 引擎不得覆盖或释放 |
| 页 1 | 引擎目录，魔数 `META` | 保存所有表结构及每张表的数据页号列表 |
| 数据页 | 每页一条记录，魔数 `ROW1` | 由引擎编解码，经存储模块分配和回收 |

目录页依次编码：`META`、表数量，以及每张表的表名、列数量、各列名称及类型序号、数据页数量、数据页号列表。字符串使用四字节 UTF-8 字节长度加字符串内容；整数采用大端序。

目录只有 4096 字节，且每条记录的页号也要占目录空间。因此容量不仅受表和列数量影响，也受记录总数影响。超限会抛出 `catalog exceeds one page`，不能认为数据可以无限增加。

记录页格式如下：

| 字节位置 | 长度 | 内容 |
| --- | --- | --- |
| 0–3 | 4 字节 | 魔数 `ROW1` |
| 4 | 1 字节 | 有效标记，插入时为 1 |
| 5–8 | 4 字节 | 记录载荷长度，大端整数 |
| 9 起 | 可变 | 按 schema 列顺序写入的值 |

载荷中 INT 占 4 字节，FLOAT 使用 Java double 占 8 字节，BOOL 占 1 字节，VARCHAR 使用四字节长度加 UTF-8 内容。一行载荷最多 4087 字节，尚不支持跨页大字段、NULL 位图、槽位目录或格式迁移。

### 4.3 写入、读取和删除

1. 建表：检查存储目录中的重复表名，登记 schema，序列化并刷写目录页。
2. 插入：按 schema 编码行，检查长度，分配一页，构造页头并写入缓冲池，再登记页号并刷写目录页。
3. 扫描：遍历该表的页号列表，读取各页，检查部分页头信息，按 schema 解码为 `Row`。
4. 删除：将待删除行与页内记录按值比较，匹配后调用 `freePage` 并移除目录中的页号，最后保存目录。同值记录通过逐个消耗待删除列表中的匹配项处理，目前没有稳定记录 ID。
5. 关闭：保存目录，再调用 `bufferPool.close()` 刷写剩余脏页。正常关闭重开已有集成测试覆盖。

读取到的页是副本，修改后必须显式调用 `writePage`。目录页当前立即刷写，记录页可能仍留在缓存中；上述步骤没有原子提交保障，正常关闭后的持久化不能等同于断电恢复能力。

## 5. 表目录与 CLI 如何协作

目录分为两种用途：编译器 `Catalog` 保存用于语义分析的表结构；引擎 `TableData` 还保存持久化所需的数据页号。`loadInto` 将持久化表结构导入编译器目录，页号仍留在引擎内部。

`CatalogManager` 是可选封装：构造时可恢复目录，`findTable` 查询内存结构，`registerTable` 先登记内存再调用存储建表。当前 CLI 直接调用 `loadInto`，没有经过该封装；后续需要统一目录更新入口，并处理存储失败后的内存状态。

`cli/Main` 将命令行参数拼成 SQL，使用默认文件 `data.db`，打印优化计划及查询行，通过 try-with-resources 关闭存储。编译错误和运行时错误分别输出“编译失败”和“执行失败”，退出码为 1。当前没有交互式命令循环、数据库路径选项、结构化结果表格或事务命令。

## 6. 后续负责什么、建议如何做

以下是建议方案，均尚未实现；新增功能代码必须放在 `engine/`。

| 工作 | 建议实施方式 | 验收重点 |
| --- | --- | --- |
| 失败一致性 | 在修改内存表目录和分配页前尽量完成校验；失败时撤销本次登记及资源分配；使用临时编译目录 | 目录超限、写入失败或编译失败后，无虚假表和泄漏页 |
| 目录扩容 | 在 `storage_engine/` 中设计带版本的多页目录，使用已有页 API 维护链和根入口 | 大量表及记录、重开恢复、旧格式识别 |
| 记录页升级 | 在引擎中实现槽式页、稳定 RecordId、空闲空间管理；明确大字段策略 | 一页多行、重复值精确删除、页复用、长度边界 |
| 损坏检测 | 统一验证魔数、长度、类型及页号；给出明确损坏异常 | 损坏目录或记录不能静默变成空库或遗漏数据 |
| 事务与恢复 | 在引擎新增事务上下文，设计日志、提交点和重放/撤销协议；先核实已有存储 API 的写回及持久化保证 | 失败回滚、进程异常退出、目录与数据一致、恢复幂等 |
| 并发控制 | 先建立同库共享的访问入口和锁，明确语句或事务边界；随后再决定表锁、行锁或版本控制 | 扫描后删除不可被并发写入破坏，多实例访问有明确约束 |
| 执行性能 | 将物化列表改为迭代器，减少中间结果；目录页号列表与记录定位同步调整 | 大表内存上限、扫描正确性、资源释放 |
| CLI 与结果接口 | 增加执行结果类型，返回列信息、查询行和影响行数，再完善交互及路径配置 | 查询和写操作输出清晰，失败退出码及资源关闭正确 |

当前方法级 `synchronized` 不能保护“扫描后删除”这一完整语句，也不能协调不同 `PageStorageEngine` 实例或进程。当前 `requireTable` 还会自动为未知表登记元数据，目录读取失败存在忽略异常的路径，后续应明确这些行为，避免将容错当作一致性保障。

`UPDATE`、表结构变更、JOIN、排序和聚合等扩展依赖编译器是否提供相应 AST 和 Plan，不能只在执行器里增加分支就宣称 SQL 已支持。若确认现有公开 API 无法满足需求，先在 [受保护模块变更方案目录](protected-module-change-proposals/README.md) 新增方案，说明现状、阻塞点、建议 API、兼容性影响、调用方改动和验证方式，等待负责人批准并由负责人实施。不得直接修改受保护模块。

## 7. 开发顺序与验证

建议先稳定现有建表、插入、查询和删除的边界行为，再处理目录扩容及记录布局，随后建设事务恢复和并发控制。CLI 结果接口可以在现有执行接口之上独立完善。

使用 Java 21、Maven 和 UTF-8。在项目根目录执行：

```powershell
mvn test
```

已有 `EngineIntegrationTest.executesCrudAndRestoresCatalogAfterRestart` 验证基本 SQL 执行及正常关闭重开。它不覆盖 UPDATE，也不证明事务、并发、崩溃恢复、所有表达式或容量边界正确。新增执行算子必须在 `engine/src/test/java` 补测试；持久化改动应增加重开与失败场景，事务和并发实现应增加故障注入与并发测试。

SQL 示例及语法范围参见 [SQL_SUPPORT.md](SQL_SUPPORT.md)。其中多语句时序应按本文所核对的“整批编译成功后按序执行”理解；目录容量也需计入每条记录的页号开销。
