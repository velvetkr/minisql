# MiniSQL 编译器 · 答辩手册

> 用途：现场验收前通读。按「一句话总览 → 分模块讲解 → 关键函数 → 现场应对 → 高频提问」组织。
> 记住一个主线（PPT 第 43 页）：**SQL → Token → AST → Semantic → Plan → Optimize**，每一层都是"把上一层的产物翻译成下一层"。

---

## 一、一句话总览

这个项目做的是数据库系统的**前端编译器**：输入一段 SQL 文本，依次经过词法分析、语法分析、语义分析、计划生成、规则优化，最终输出一棵**优化后的逻辑执行计划树**。它不真正执行 SQL（不碰磁盘数据），执行引擎是后续模块的事——但它产出的计划会直接驱动执行引擎。

---

## 二、分模块讲解（每块：是什么 → 输入/输出 → 核心思路 → 可能的坑）

### ① 词法分析 Lexer（`lexer/`）

- **是什么**：把一串字符，机械地切成一个个有意义的 Token（词法记号）。
- **输入 → 输出**：`"SELECT * FROM student"` → `[SELECT, STAR, FROM, IDENT(student)]`。
- **核心思路**：从左到右读字符，遇到"一段有意义的东西"就切一个 Token，同时记下它的行列位置。
- **Token 的三个信息**（PPT 第 8 页）：`type`（什么类型，给 Parser 看）、`lexeme`（原始文本，保留值）、`line/column`（位置，给报错用）。
- **难点（PPT 第 9 页）**：多字符运算符 `>= != ==`、字符串转义 `'Tom''s book'`、`--` 注释、关键字大小写不敏感、非法输入要报错不崩溃。
- **实现**：`Lexer.tokenize()` 循环调用 `nextToken()`；关键字用一个 `Map<String,TokenType>` 查表（先转小写）。

### ② 语法分析 Parser（`parser/` + `ast/`）

- **是什么**：把 Token 流按文法拼成 AST（抽象语法树），而不是只判断"合不合法"。
- **输入 → 输出**：Token 流 → `List<Statement>`（AST 树）。
- **核心思路**：**递归下降**——文法里每个非终结符对应一个 Java 方法，方法之间互相调用。
- **关键：表达式优先级**（PPT 第 13/18 页）。用"一层一个方法"实现，优先级从低到高：
  `parseOr → parseAnd → parseNot → parseComparison → parseAdditive → parseMultiplicative → parseUnary → parsePrimary`。
  `a = 1 OR b = 2 AND c = 3` 会解析成 `OR(=(a,1), AND(=(b,2),=(c,3)))`，AND 更贴叶子。
- **左递归问题**（PPT 第 14 页）：递归下降要求文法无左递归，所以用"`while` 循环 + 内层方法"的方式消掉左递归。

### ③ 语义分析 SemanticAnalyzer（`semantic/` + `catalog/`）

- **是什么**：让"语法正确"进一步变成"语义可执行"——查表、绑列、查类型。
- **五件事**（PPT 第 24 页）：表存在性、列存在性、**名字绑定**、**类型一致性**、INSERT 匹配（列数/顺序/值类型）。
- **核心思路**：拿着 `Catalog`（符号表）逐条语句检查。Catalog 就是编译原理里的"符号表"，存"表名 → 表结构"。
- **两个关键函数**（下面第 3 节细讲）：
  - `resolveColumn`：把列名绑定到 Catalog 里的具体列定义，列不存在就报 `SemanticError`。
  - `typeOf`：递归推导表达式类型，同时做类型检查（`INT + VARCHAR` 直接报错）。
- **类型规则集中管理**（PPT 第 27 页）：所有"谁和谁能运算"的规则都写在 `SemanticAnalyzer` 的一组辅助方法里，不散落。

### ④ 计划生成 Planner（`plan/`）

- **是什么**：把 AST 翻译成**逻辑执行计划树**（算子树），这是编译器和执行引擎的接口。
- **5 种 Plan 节点**（PPT 第 30 页）：`CreateTable`、`Insert`、`SeqScan`（扫表）、`Filter`（WHERE）、`Project`（选列）。
- **核心思路**：`SELECT ... WHERE ...` → `Project(选列) → Filter(条件) → SeqScan(表)`（PPT 第 31 页）。DELETE 复用 `Filter → SeqScan`（SeqScan 标 DELETE）。

### ⑤ 规则优化 Optimizer（`optimizer/`）

- **是什么**：对计划做"结构等价变换"，让它更高效但语义不变。
- **5 条规则**（PPT 第 33 页）：
  1. **常量折叠**：`10 + 8` → `18`；
  2. **布尔化简**：`TRUE AND x` → `x`；
  3. **投影裁剪**：Project 只保留需要的列（去重）；
  4. **谓词下推**：Filter 尽量靠近 SeqScan；
  5. **冗余节点消除**：删掉恒真 Filter。
- **经典例子**（PPT 第 34 页）：`WHERE 1=1 AND age>10+8` 优化成 `age>18`。
- **重点**：不是"优化多复杂"，而是**规则正确、前后结构可验证、语义等价**。

### ⑥ JSON 序列化（`serialize/`，扩展加分项）

- **是什么**：把 AST 和 Plan 再输出一份 **JSON 文本**。这是「扩展加分项」，对应 PPT 第 30 页对 Plan 输出形式的要求——「树形 / JSON / S-expression，任选其一，但结构必须明确」。
- **为什么做**：之前 Plan 只有「树形」（给人看）；JSON 是「给程序看」的机器可读形式，可以喂给前端可视化工具、或让下游系统直接解析。两种形式讲的是**同一棵树**，只是呈现不同。
- **核心思路**：`JsonPrinter` 用 `instanceof` 逐个识别节点类型，递归拼出带 `"kind"` 字段的 JSON。语句/计划用多行缩进，表达式用单行紧凑；纯字符串拼接、**零第三方依赖**。
- **答辩要点**：现场若问「Plan 的 JSON 和树形是什么关系」，就回答——**同一棵树、两种视图**，JSON 是序列化的、可持久化/可传输的形式；两者都能从 `Plan` 递归生成，不改变 Plan 本身的结构。

## 三、关键函数（PPT 第 40 页会随机点）

### 1. `parseExpr`（语法分析，`Parser.java`）

老师可能叫它 `parseExpression`——指的就是表达式入口 `parseExpr()`。它只做一件事：

```java
private Expr parseExpr() { return parseOr(); }
```

然后 `parseOr → parseAnd → ...` 一路下沉。**讲解要点**：入口直接交给"最低优先级的 `parseOr`"，由它往下逐层调用；每层用 `while` 循环收集同优先级的运算符，遇到更高优先级就交给更内层的方法。所以优先级是"写死在方法的嵌套关系里"的。

### 2. `resolveColumn`（语义分析，`SemanticAnalyzer.java`）

```java
public ColumnDef resolveColumn(Table table, String columnName, int line, int column) {
    ColumnDef col = table.findColumn(columnName);
    if (col == null) throw error("列 '" + columnName + "' 不存在于表 '" + table.name + "'", line, column);
    return col;
}
```

**讲解要点**：这就是 PPT 第 26 页"名字绑定"。标识符在 AST 里只是一个字符串（`"age"`），语义分析阶段要回答"它到底指向哪张表的哪一列"。答案存在 Catalog 里；找不到就报带行列的 `SemanticError`。

### 3. `buildPlan`（计划生成，`Planner.java`）

```java
public Plan buildPlan(Statement stmt) {
    if (stmt instanceof SelectStmt) return buildSelect((SelectStmt) stmt);
    ...
}
```

**讲解要点**：AST 是"语法树"，Plan 是"算子树"。`buildPlan` 把四种语句各自翻译成对应的算子组合。SELECT 是最典型的：先造最底层的 `SeqScan`，有 WHERE 就包一层 `Filter`，最后包一层 `Project`，自底向上搭起来。

## 四、现场验收应对（PPT 第 40 页四种形式）

### 形式 1：随机讲解函数
准备：能不看代码说出 `parseExpr` / `resolveColumn` / `buildPlan` 的"一句话职责 + 大致流程"（见上一节）。

### 形式 2：现场改需求
| 需求 | 现状 | 怎么加 |
|------|------|--------|
| 加 `<=` | **已支持** | `Lexer` 有 `LE`、`Parser.isComparisonOp` 含 `LE`，无需改 |
| 加 `NOT` | **已支持** | `parseNot` 已处理 |
| 加 `DISTINCT` | 未支持（`TokenType` 已预留 `DISTINCT`） | ① `Parser.parseSelect` 识别 `DISTINCT`，② `SelectStmt` 加字段，③ 语义/计划相应处理 |

**应对思路**：先定位到"改哪一层"——语法改动在 `Parser`、AST 结构改动在 `ast/`、检查改动在 `SemanticAnalyzer`、计划改动在 `Planner`。这是"模块边界清晰"（PPT 第 5 页"可扩展"）的直接体现。

### 形式 3：现场 Debug
给一条失败 SQL，判断属于 Lexer / Parser / Semantic / Plan 哪一阶段。判断口诀：
- 报错在**拼出 Token 之前**（非法字符、字符串没闭合）→ Lexer；
- Token 都认得但**拼不成语法**（缺分号、括号不对）→ Parser；
- 语法对但**表/列不存在、类型不对** → Semantic；
- 前三个都过、**计划树不对** → Planner。
实际运行时，报错前缀已经直接告诉你了：`LexerError / SyntaxError / SemanticError`。

### 形式 4：AST / Plan 推导
给一条新 SQL，现场画关键 AST 或 Plan。练几个：
- `SELECT a, b FROM t WHERE a > 1 AND b < 2;` → Plan：`Project[a,b] → Filter[a>1 AND b<2] → SeqScan[t]`
- `DELETE FROM t WHERE x = 0;` → Plan：`Filter[x = 0] → SeqScan[t] (DELETE)`

## 五、高频提问 + 参考回答

**Q1：为什么用递归下降，不用工具生成？**
递归下降直观、好调试、和文法一一对应，适合教学；而且我们的表达式文法消左递归后正好能用递归下降写（PPT 第 14/19 页）。

**Q2：Token 为什么要有 line/column？**
为了错误定位。没有位置，报错只能说"有错"；有了位置才能说"第几行第几列错了"，这是"像真正编译器一样"的关键（PPT 第 10 页）。

**Q3：Catalog 和 AST 里的表信息有什么区别？**
AST 里表名只是一个字符串；Catalog 才是"真正知道这张表有哪些列"的地方。语义分析靠 Catalog 把 AST 里的名字"绑定"到真实结构上。

**Q4：常量折叠为什么要在优化阶段，而不是 Parser 阶段？**
Parser 只负责"把语法结构搭出来"，不关心值；优化阶段才做"等价改写"。职责分离，模块边界清晰。

**Q5：优化后怎么保证语义等价？**
每条规则都是"数学/逻辑上恒等"的局部改写（`1=1` 恒为 TRUE、`TRUE AND x` 恒等于 `x`），所以整体语义不变，只是结构更精简。

**Q6：DELETE 为什么没有独立的 Plan 节点？**
PPT 规定的 5 种节点里没有 Delete。DELETE 的语义是"扫描 + 过滤出要删的行"，正好用 `Filter + SeqScan`（SeqScan 标 DELETE）表达，不额外造节点。
